### Branch naming — the branch name *is* the version

A branch is named for the version it produces: `v0.2`, `v0.4.14`, `v1.4.1`, `v1.5.0`, `v1.5.1`. Never `feature-*`. Bump `ucando.__version__` on the branch so the running app, `/api/info`, the UI chip, the packaged zip name and the branch all report the same number — a build handed to someone else is otherwise impossible to place. **A version that has been packaged and shared is closed**: start a new branch (next patch number) rather than adding to it, so the artifact and its branch keep matching.

What the branch *contains* goes in its **git branch description**, not its name (`git config branch.<v>.description`, or `git branch --edit-description`). Read them with `git config --get-regexp '^branch\..*\.description$'`. Each one ends with a "Next" line naming the branch that should follow, so the plan survives between sessions.

The bus carries **no per-frame checksum** but a 2-bit rolling counter in six frames, and duplicates safety signals inside the frame. `0x500` broadcasts the **VIN in ASCII** — WMI `MA3` confirms the make from the bus itself. See `docs/SUZUKI_DZIRE_DECODE.md`.

**🔒 Gateway-isolated OBD port — the case uCANdo currently cannot serve (2026-08-20):** a **2026 Maruti Suzuki Dzire** broadcasts **nothing** on its OBD-2 port. A 338 s capture contains exactly four IDs — `0x7DF`/`0x7E0` requests and `0x7E8`/`0x7EE` responses — and not one vehicle broadcast frame (no `0x120`, `0x124`, `0x310`, `0x460`, `0x500`). A passive listener sees an empty bus and that is *correct*; the "other analyzer" that shows data is a **scan tool actively polling** (a Teltonika FMB001, visible in the capture because the neoVI sniffed the same wire). This is a gateway decision, not a wiring/bitrate fault — Vehicle Spy reports "No Bus Errors". **The capability gap this exposes:** `Dashboard` is fed by a bus *tap* and never asks, so it stays empty forever on a gated car; the poll loop exists only in `cli.py cmd_drive`; and **nothing in the codebase transmits an ISO-TP flow-control frame**, so uCANdo can *watch* a multi-frame UDS read but cannot perform one. The VIN on this car is reachable **only** via UDS `22 F190` on the physical address (Mode 09 was ignored). Three fixes — an active PID poller in the server, an ISO-TP tester, and a UI that says "no broadcast traffic, this port may be gated" instead of looking broken. **No pack exists for this vehicle by design.** See `docs/SUZUKI_DZIRE_2026_GATEWAY.md`.

**🏁 First vehicle in motion — speed and odometer finally provable (2026-08-20):** a **Hyundai Aura** capture set: 17 Vehicle Spy files, 30 IDs, 11 event-isolated captures **plus four MOVING files with the odometer written down either side** (`Moving/odo.txt`: 40241 → 40243). Every pack before this had speed and the odometer quantum stuck at Tier C because no vehicle had ever been driven. Now: **odometer `0x5B0` ×0.1 km confirmed**, and **vehicle speed `0x200` + four wheel speeds `0x386` proved at 1/32 km/h by integrating against the recorded distance** (1.14-1.16 km vs 1.10, inside the odometer's own ±9 % quantisation; four wheels agreeing within 0.3 km/h is what identifies the frame). The captured car turned out to be a **petrol+CNG bi-fuel** Aura (OBD PID 51 = fuel type 13, and the cluster shows CNG active with the petrol gauge near empty), *not* the petrol car of the existing pack — so it is its own leaf folder `Aura/CNG_2024/` and `Petrol_2023` keeps its original three signals. **Fuel and CNG level could not be identified**: the car ran on CNG throughout, so petrol never moved and CNG barely did, leaving ~25 equally-good constant bytes; and the device's 86 % came from an OBD *request*, not a broadcast frame, so it is not a known-value match. **The arithmetic trap worth remembering:** the dash floors to whole km, so the *displayed* 2 km over 11 raw counts suggests 0.18 km/count — wrong; 0.1 is the only scale reproducing both displayed integers and a sane absolute reading. Two signals moving in *two* captures are confirmations, not failures: `ClutchPedal` moves in the clutch **and gear** captures (you press the clutch to change gear) and `BrakePedal` in brake **and parking-brake**. Open: coolant is unidentifiable while every capture sits at operating temperature — **a cold-start capture would isolate it in one run**. See `docs/HYUNDAI_AURA_DECODE.md`.

> **Passive capture bounds what can ever be found.** The Aura's VIN, MAF, throttle and DTC count were all visible on a Teltonika yet absent from 17 Vehicle Spy files, because the device *asks* (OBD request/response) and the captures only *listen*. The same ISO-TP reassembly recovered the 2026 Dzire's VIN in full — there a tool was on the bus. **Run the scan tool and the sniffer at the same time** and correlation turns those PIDs into broadcast-signal identifications in one pass, which is exactly how the WagonR got four Tier-A signals.

> **A pack DBC holds only signals you can name.** Empty frames, constant bytes, power-up one-shots and unidentified byte dumps go in the `docs/` RE record, not the database — see "What belongs in a pack DBC" in `oem_packs/README.md`. This is free: `signature.json` is capture-derived and independent of the DBC, so the Dzire pack went 41 messages → 13 with its identify score unchanged at 1.000.

## Commands

**Run the app** (a source run serves the UI at `http://127.0.0.1:8865` and opens the browser):
```powershell
python main.py                       # default
python main.py --port 9000 --no-browser
python main.py --reload              # dev auto-reload (uvicorn)
```
**Release and dev side by side** (user skill `utility-ui` §11): `ucando/channel.py` keys what the
two could fight over on the channel — the packaged exe is `release` on **8765**, a source run is
`dev` on **8865** (`--port` still wins). Data folders are already separate (exe → beside itself,
source → repo `data/`), the banner and tab title mark *Dev*, and usage reporting is release-only.
A second start of the same channel finds uCANdo on the port (`main.probe` → `/api/info`) and just
opens the browser there instead of failing to bind; a port held by another program is named.

**Install dependencies** — there are two Python installs on this machine (3.12 and 3.14). Pin one with a venv so `python main.py` and the VS Code interpreter never diverge:
```powershell
python -m venv .venv
.\.venv\Scripts\Activate.ps1
pip install -r requirements.txt
```
Per-hardware extras are intentionally *not* in `requirements.txt`: `pip install python-ics` for Neo VI; PCAN needs the OS-level PEAK PCAN-Basic driver.

**Drive the UI** after a UI change (a private copy on its own port and data folder, virtual bus with the simulator; every view in dark and light, Settings, the three Sidebar modes, a 900 px window — fails on any page JavaScript error, screenshots in `%TEMP%\ucando-shoot\shots` to look at):


## Architecture

uCANdo is a hardware-agnostic CAN bus workbench: a **FastAPI backend + WebSocket + static single-page web UI** (no JS build step — plain `web/*.{html,css,js}`). The same app drives three adapters plus a development virtual bus.

### The central invariant: everything talks to the HAL, never to `python-can` directly

`hal.py` defines `CANInterface` (ABC: `send`/`recv`/`close`) and `create_interface(hw, channel, bitrate, fd)`, a factory that maps a hardware key → a `python-can` interface string via the `BACKENDS` table. **No module above the HAL imports `can.Bus`** — they hold a `CANInterface`. This is what makes "one utility, any adapter" work; preserve it when adding modules.

Hardware keys and their backends (`BACKENDS` in `hal.py`):

| key | python-can interface | channel | notes |
|---|---|---|---|
| `virtual` | `virtual` | `"ucando"` (str) | dev; in-process broadcast |
| `neovi` | `neovi` | `1`/`2`… (int) | needs `ics` lib |
| `pcan` | `pcan` | `"PCAN_USBBUS1"` (str) | needs PCAN driver |
| `microchip` | `slcan` | COM port (str) | analyzer flashed with SLCAN firmware |

Channel type is coerced per-backend (`channel_type` in the table), and `fd` is only forwarded to backends with `supports_fd`. The one exception to "no `can.Bus`": `device_enum.py` and `sim.py` use `can`/vendor libs directly, by necessity (enumeration and traffic generation sit *beside* the HAL, not above it).

### Foundation rails (Phase 0)

Four cross-cutting modules added to keep the app extensible without editing core (see `docs/PRODUCT_PLAN.md`):
- `registry.py` — generic `Registry` + the named global registries `RE_ENGINES`, `DECODERS`, `EXPORTERS`, `OEM_PACKS`. New engines/decoders/exporters/OEM packs **self-register** at import; `load_plugins()` auto-imports everything under `ucando/plugins/`. `server.py` calls it once and exposes `/api/plugins`. The `Protocol` classes in `registry.py` are the documented plugin contracts.
- `storage.py` — thread-safe SQLite (`Storage`, WAL, one lock for writes). Schema is a plain list of `CREATE TABLE IF NOT EXISTS` strings — append one to extend. Tables: `oem_profiles` (the India OEM DB + frame `signature` for auto-ID), `vehicles`, `captures`, `jobs`, `settings`.
- `config.py` — `Config` over the `settings` table with `DEFAULTS`; named profiles are namespaced `profile:<name>` keys. `server.py` exposes `/api/config`.
- `contracts.py` — `TypedDict` definitions of the `snapshot()` / `/ws/live` payload, the **single source of truth** for the backend↔`web/app.js` coupling. `check_snapshot()` lets tests assert the producer keeps the contract. Update this + `web/app.js` together when the snapshot shape changes.

### Reverse-engineering engines (Phase 1)

RE is pluggable. `reverse.py` now only does log I/O (`load_log_frames` → the *frames-by-id* shape `{(id,ext): {timestamps, payloads}}`) and dispatches `analyze_log(path, engine=...)` through `RE_ENGINES`. Engines are pure/bus-free and self-register via `ucando/plugins/builtin_engines.py`:
- **`read`** (`re_engines/read.py`) — the default. Bit-flip-rate (BFR) tokenization: finds signal boundaries where BFR drops (one signal's LSB abutting the next's MSB), infers endianness (big-endian from contiguous MSB-first bits; little-endian by counter-fit or smoothness), and classifies each span constant/counter/crc/multi-state/physical. Also `detect_multiplexor`. Output is a **superset** of the legacy shape (keeps `bytes[].{index,kind,entropy}` and `candidates[].{start_bit,length,name,byte_order}` that `web/app.js` reads) plus `kind`/`bfr`/`confidence`/`step`.
- **`basic`** — the original toggle-count finder (`reverse.BasicEngine`), kept for comparison.

`re_engines/diff.py` adds the **state-change sniffer** + **log compare**: `diff_frames(baseline, after)` reports per-ID which bits were constant before but changed after (→ contiguous `event` candidates). `StateSniffer` is the live, guided version — a bus tap registered in `server.py` (`bus.add_tap(sniffer.consume)`), driven by `arm`→`mark`→`result`. RE endpoints: `/api/re/engines`, `/api/re/analyze` (takes `engine`), `/api/re/sniff/{arm,mark,stop,status,result}`, `/api/re/compare`, `/api/re/promote` (seed DBC from any RE id-result, with a `min_confidence` filter).

### OEM CAN Database (Phase 2, Pillar A)

`oem_db.py` — `OemDatabase` over the `oem_profiles` table: CRUD, DBC import/export, and **save-from-DBC-builder** (the RE flywheel). Each profile carries a `dbc` + a frame **signature** (`{id_set, ids[{id,ext,dlc,period_ms}]}`). `fingerprint_frames`/`fingerprint_from_id_stats` build a signature from a log or a live `snapshot()`; `identify_from_signature` scores it against every profile (Jaccard of ID sets + DLC bonus → ranked **CANMatch-style** matches). `seed_builtins()` (called once in `server.py`, idempotent) inserts every `oem_packs/` vehicle plus a decodable **"Sim Vehicle"** profile matching the simulator — **only decodable rows are ever created**; an uncovered OEM appears in `TARGET_OEMS` (the UI's coverage list), never as an empty profile. `prune_blank()` runs alongside it at startup (and behind the Profiles panel's "Clean up" button / `/api/oem/prune`): a row with no signature IDs *and* no messages in its DBC can neither be applied nor identified against, so it is deleted; a row whose DBC parses but whose signature is empty is **repaired**, not dropped. `list_profiles` reports **`id_count` (bus fingerprint) vs `msg_count`/`signal_count` (what the DBC decodes)** — they differ on purpose (Windsor: 120 IDs seen, 55 messages decodable), counted by a `BO_ `/`SG_ ` line scan (`_dbc_counts`) rather than a cantools parse so listing every row stays cheap; `year` comes from `year_min/year_max` with a fallback that reads a year out of the profile name (RE-saved rows have no year columns). `profile_signals(pid)` expands one profile's DBC into messages + signals for the list's click-through. Endpoints: `/api/oem/profiles`, `/api/oem/profile{,/update,/delete}`, `/api/oem/profile/{pid}/signals`, `/api/oem/prune`, `/api/oem/import`, `/api/oem/from-builder` (**endpoint only — no UI entry**), `/api/oem/identify` (live), `/api/oem/identify-log`, `/api/oem/apply` (loads a profile's DBC into the Signal Viewer → decode a known vehicle with zero RE). UI: "OEM Database" view = identify + the Profiles list, whose columns are **Make · Model · IDs · Messages · Year · Status**; clicking the **Model** cell expands an inline signal list (fetched on demand, cached in `oemDetail`, styled with the Converter's `.cv-msg`/`.cv-sigtable` classes).

### OEM-aware visualization (Phase 3)

### Dependency direction (keep acyclic)

```
hal → (device_enum, sim) → logger → bus_manager → server → web/
                                       ▲
   replay, reverse, dbc_builder, signals, scheduler, protocol ─┘  (all sit beside, wired in by server)
```
- `device_enum.py` — `enumerate_all()` populates the connect dropdown. Every `list_*` is fully guarded: a missing vendor lib/driver returns `[]`, never raises. PCAN has no enumeration API so it *probes* `PCAN_USBBUS1..8`. Microchip is detected by CP210x VID `0x10C4`; non-matching COM ports are listed but flagged "verify".
- `sim.py` — `SyntheticTraffic` opens its *own* virtual `can.Bus` on the same channel and emits four deliberately-distinct signals (sine-ramp `0x100`, monotonic counter `0x200`, high-entropy noise `0x301`, constant heartbeat `0x7DF`) so offline RE has real entropy/variance to find. Uses an LCG, not `random`.
- `logger.py` — `CanLogger` owns one background recv thread bound to a `CANInterface`. Each frame fans out under a lock to: a rolling recent-frames deque, an aggregated per-ID table (count + EMA period estimate + last payload), global stats, and any active recording writer. **Frame taps** (`add_tap`) run *outside* the lock — that's how Signal Viewer / Protocol Decoder observe live traffic without a second recv thread. `snapshot()` is the single read API the UI consumes.
- `replay.py` / `scheduler.py` — transmitters. Neither opens a bus; both take a `send` callable (`BusManager.send`) so they stay adapter-agnostic. Each runs its own daemon thread with event-based pause/stop.
- `txverify.py` — `TxRecorder` (tap on `TxEngine._message()`; per ID also `age_s`/`period_ms` on the tap's own `perf_counter` clock), cloud raw-frame importer, and `compare()` for the B-vs-C byte diff. **Transmit signal (was "On the wire") has two views** (v1.6.0, the user's ask): **Tiles** — `/api/tx/live/signals` decodes every transmitted ID the uploaded JSON/DBC describes in one call (`framedecode.decode_frame(cells=False)`: the bit layout costs a packer call per bit and tiles don't draw it), one tile per signal grouped by message, value-table text as the cloud shows it, pins (per definition, in pin order — to mirror the device's cloud panel), a change lights the tile and fades, grey once the ID's own rhythm says it stopped (`3 × period`), "Forced"/"Rewritten" when Patch rewrites it, amber edge when outside the DBC range; a tile opens its ID in **Bytes** with that signal's bits highlighted. **Bytes** — the ID list (amber mark = in the definition, **All / In DBC** filter, changed bytes lit) beside one ID's payload and bit grid. Both update in place (keyed), so a change fades instead of blinking off on the next poll. Backs the **TX Monitor** view, which renders a transmitted payload with a purpose-built lightweight bit grid (the Frame Decoder's grid is bound to its own selection state; duplicating ~30 lines beat refactoring a working view). Decodes via `jsondecode` **or** `framedecode` — same output shape, so one renderer serves both. See the TX-V section below.
- `txpatch.py` — `FramePatcher` rewrites outgoing payloads (live overrides + loop-seam continuity). Installed on the engine via `set_patcher`; `TxEngine._message()` is the single place frames are built, and `_start_item_locked` calls `on_rewind()` at **every** item boundary, not just loop points (a playlist can put an earlier capture after a later one, which steps the odometer backwards exactly like looping does). See the TX-3 section below.
- `logstore.py` — the loader behind TX replay: any log → one `FrameStore` of **packed parallel arrays** (`t`/`ids`/`flags`/`dlc`/`net`/`off`+`data`, ~27 B per frame) instead of `can.Message` objects, which would cost ~1 GB for a full drive session (100 000 frames *per* Vehicle Spy buffer file × dozens of files). `can.Message` is rebuilt lazily in `message(i)`. Two things it adds over `can.LogReader`: (1) **Vehicle Spy CSVs are detected by content, not extension** — `can.LogReader` routes `.csv` to its own `timestamp,arbitration_id,…` dialect and cannot read a neoVI export at all, so `load()` sniffs the banner and dispatches to `vspy`; (2) **every frame keeps its network index** — one Vehicle Spy file interleaves physically separate buses (a real MG Windsor capture: `HS CAN` 76 696 frames + `MS CAN` 23 304 in the same CSV), so `indices(network, ids, skip_tx)` plays exactly one of them. `network_summary()` recovers per-network **baud** (Vehicle Spy's `Network Description` table, via `vspy.network_table`), fps, ID count and a nominal **bus-load %** — that's what feeds the UI's "captured at 500 kbit/s / ~41 % load" line and the bitrate-mismatch warning. `skip_tx` drops `Tx=T` rows: frames the *capturing tool* sent, not the vehicle.
- `pcantrc.py` — the PEAK **PCAN-View `.trc`** reader behind `logstore._parse_trc`, and the reason TX can replay a workshop capture (the Dzire pack came from one). Dispatch is by *extension*, unlike vspy's content sniff, because `.csv` is ambiguous and `.trc` is not. Three things it fixes over `can.LogReader`, which does read the format: (1) **the anchor** — the `O` column is the PCAN driver's hardware timer, not an offset from `$STARTTIME`, and `$STARTTIME` is *local* wall clock in PCAN-View files but *UTC* in `can.TRCWriter` ones, so timestamps come out `anchor + (O - O_first)` with the local/UTC question settled by the file's own `;   Start time:` comment rather than guessed; (2) **direction and non-frame rows** — `Rx`/`Tx` becomes `FLAG_TX`, and `ST`/`EC`/`ER`/`EV` rows are counted into `census` and turned into `notes()` sentences instead of silently dropped (one sample capture says `Hardware plug-out` — the dongle was pulled mid-recording); (3) **the bitrate**, which no `.trc` version records — `DEFAULT_BAUD = 500_000` is assumed so bus load is estimable at all, but it travels as `baud_source="assumed"` and `TxItem.baud` overrides it as `"declared"`. `min_baud()` is the floor the file proves (frames exist, they took that long) and is used to *reject* an impossible declaration, never to guess. Network naming is `CAN <bus>` from the bus index alone — **never per file**, or `txproject`'s "playlist mixes networks" would fire on every multi-file scenario.

### TX Replay pacing (TX-1)

`replay.py`'s `TxEngine` (aliased `LogReplayer` for `cli.py`) is **deadline-scheduled, not sleep-per-frame**. Real captures leave no room for the naive loop: MG Windsor HS CAN is ~1 870 fps, a mean gap of **535 µs**, while a Windows wait returns after ~1–15 ms — so `send(); sleep(gap)` inflates every gap *and* accumulates the send cost into it, drifting further behind with each frame. Instead every frame's due time is computed from one anchor (`_epoch`/`_base`), each wake-up sends **every frame now due** as a burst, then sleeps to the next deadline (never less than one tick — the OS can't honour shorter). Error therefore can't accumulate: a late wake-up is absorbed by the next burst instead of shifting all later frames. `timeBeginPeriod(1)` is held for the duration of playback. Measured on the real capture: **1 867 fps achieved vs 1 869 target, 0.6 ms drift over 8 s, 0.1 % of frames >5 ms late, bursts ≤24**. Jitter is reported (`health.max_late_ms`, `late_pct`, `burst_max`), never hidden — a burst is re-serialised by the bus at line rate, so receivers see correct order and slightly compressed spacing.

### TX playlists (TX-2)

`txproject.py` is the scenario model: a `TxItem` per log (path, network, repeat, ID filter, trim window, lead-in gap, label) resolved by `build()` into a `TxPlan` of `Segment`s — a loaded `FrameStore` plus the exact frame indices to send. **A single file is a one-item plan**, so `TxEngine.load()` is just `set_plan([TxItem(path)])` and every downstream key keeps its single-file meaning; nothing in the UI or CLI needs to know about playlists it isn't using. Segments are *referenced* per pass, never copied, so `repeat: 1000` costs no extra memory, and a path listed twice is parsed once (`segs[0].store is segs[2].store`).

The engine walks the plan by `(item, item_pass, cursor)`. **A lead-in gap is implemented as a later epoch** (`_start_item_locked` rebases to `now + gap/speed`), so the ordinary deadline path sleeps through it and the scheduler needs no concept of gaps. `gap_before_ms="auto"` reconstructs the real pause between two chunks of one capture session — same folder, next file's first timestamp after this one's last, ≤ `_AUTO_GAP_MAX_S`; across unrelated sessions the timestamps aren't comparable so auto means 0. On the real Windsor drive auto resolved to ≤2 ms, correctly detecting that the 33 buffer saves are contiguous. Plan-level `warnings` catch what can't work: mixed bitrates, mixed networks, an endless item that starves later ones, a trim or filter that selects nothing, overlapping files.

The whole timeline is `sum(item.repeat × (gap + duration))` per plan pass, which is what lets drift, progress and the deadline clock stay one concept across a 33-file playlist. `progress` is time-weighted across the plan (a 40 s item shouldn't advance the bar as fast as a 4 s one); `item_progress` is the current file alone. Scenarios persist as namespaced settings keys (`txplan:<name>`, same trick as config profiles) — `/api/tx/{plan,save,load,delete,scenarios}` and `python -m ucando.cli tx --scenario x.json` for unattended bench soaks.

### TX↔cloud verification (TX-V)

`txverify.py` answers "are the bytes the TCU reported the bytes we sent?". It keeps **three** artifacts apart, and that separation is the whole design: **A** the log file (what the vehicle sent), **B** what uCANdo put on the wire, **C** what the device reported to the cloud. The claim under test is **B == C**. Comparing A against C is the trap — when they differ you cannot tell whether uCANdo altered something or the TCU misparsed it, so you debug the wrong side.

`TxRecorder` taps `TxEngine._message()` — the single place a transmitted frame is built — and records **post-patch** bytes on purpose: the question is whether what left the machine arrived, not whether the file arrived. A broken tap can never break a transmit (it is wrapped). `bus.connect(echo_tx=True)` sets `receive_own_messages` so the logger *witnesses* the wire rather than trusting the `send()` record; it is off by default because it would double-count our own traffic in normal capture stats.

`compare()`'s headline number is **`unknown_payloads`**: a payload the cloud reported for an ID *we did send*, that we never sent. That is the only outcome meaning corruption. Everything else is named rather than lumped in — `sampled` (a TCU forwards a subset; normal), `not forwarded`, `unexpected id` (arrived but we never sent it — another node on the bench bus, reported as a warning, **not** as corruption; getting this order wrong made a second ECU look like a corruption bug). Per ID it also walks the cloud sequence forward through ours within `ALIGN_WINDOW`, so a report points at the *first* divergence with both payloads — the evidence a firmware bug report needs. The report always states `patched_signals` and `tx_filters` explicitly: a byte-fidelity claim is void if we rewrote signals on the way out, and "missing IDs at the cloud" is meaningless if we filtered them ourselves (MS CAN).

**We never inject a sync/marker frame to align the streams** — that would be a manipulation of the transmitted data, which is the one thing this exercise exists to rule out. Alignment is by content. Note the synergy with TX-3: a looped replay repeats payloads, making alignment ambiguous, but a monotonic odometer makes each pass unique.

**Footgun, tested in `test_signature_json_id_base_is_a_real_footgun`:** a bare `"244"` key in a cloud Signature JSON is **decimal**, so it describes frame `0xF4`. Point the verifier at an unpadded export and every ID silently fails to match, which looks exactly like a TCU dropping everything. `jsondecode.detect_id_base` decides per *file* (a `0x` prefix, a hex letter, or zero-padding anywhere ⇒ hex) — feed it the padded export rather than patching the reader.

### TX signal patching (TX-3)

`txpatch.py` rewrites payloads on their way out, for the two things a finite recording cannot do on a bench: **force a signal to a value while the log plays** (`SOC = 8 %` to trigger a TCU alert without draining a battery) and **survive a loop seam** (the Windsor log ends at 3075 km and restarts at 3066 — a receiver that sanity-checks the odometer sees a vehicle that teleported).

**Patches write raw bits, never `decode_message` → edit → `encode_message`.** The round-trip is wrong twice over: it **zeroes every bit the DBC doesn't describe** (real payloads carry unmapped bits, and an RE-derived DBC describes only some), and it costs hundreds of µs when the budget is 535 µs *per frame*. `pack_signal`/`unpack_signal` touch only the signal's own bits — Intel via a little-endian int shift at `start`, Motorola by converting the DBC start bit to a sequential MSB-first index (the same self-inverse `(x//8)*8 + (7-x%8)` as `jsondecode`/`dbc_builder`). The bit math is tested **against cantools as the oracle**, plus an explicit test that every other signal in the message is untouched. `Field` resolves layout/scale/offset once at setup so nothing parses in the hot path; a frame with no rule costs one dict lookup and is returned unchanged (`None` means "send as captured", and a test asserts an unconfigured patcher is byte-identical).

Rule kinds: `set` (hold a value — takes effect on the very next frame, safe to change mid-play), `counter` (regenerate from a running total, so it is seamless *by construction* and doesn't reset at a loop), and `monotonic`. Monotonic **only corrects backward steps**: at a seam it re-anchors to the last value sent, but a *forward* jump is left alone because that is often real driving — a playlist of non-consecutive chunks legitimately skips kilometres, and flattening it would erase distance the vehicle covered. Out-of-range values **saturate rather than wrap** (a wrapped "119 °C" would read as a plausible cold temperature). Checksums are opt-in and byte-aligned-8-bit only (`sum8`/`xor8`): a vehicle's real algorithm is usually proprietary, so guessing one silently would be worse than leaving the captured byte alone.

`analyze_many(sources, db)` finds candidates from *behaviour in the log*, not DBC names — and takes **several** playlist items, because one chunk is not representative: the MG odometer is **constant through the opening 41 s file** (the car hadn't pulled away), so scanning item 1 alone reports no odometer at all. `/api/tx/patch/analyze` therefore samples `_ANALYZE_SEGMENTS` items spread across the playlist. Names in `_ACCUMULATOR_HINTS` only *rank* the list and never select: a battery temperature that drifted up over 41 s is genuinely monotonic in the data and would be wrong to accumulate on a loop, so the UI pre-checks nothing and marks hinted rows with ★.

**Parsing is cached** (`logstore.cache_path`, keyed on path+size+mtime, JSON header + raw array bytes, atomic `os.replace`): building the 33-file plan drops from 65 s to 2.5 s. Every failure path — missing, truncated, corrupt, written by a Python whose `array("L")` is a different width — falls back to parsing, so the cache can cost time but never correctness.

Two things that look like bugs but are load-bearing: **drift is banked per speed segment** (`_close_segment_locked` on `set_speed`) because log time played at 5× owes a fifth of the wall clock — one `log_time / current_speed` division would rewrite history the moment the speed knob moves; and **health freezes on stop/done/error** (`_freeze_locked` stores *both* elapsed and expected) because `stop()` rewinds the cursor, so a live-computed "expected" would collapse to zero and report the whole run as drift. `_MAX_CONSEC_ERRORS` send failures in a row (no ACK / bus-off / a full transmit queue / adapter yanked) put playback in **`state="recovering"`, never `error`** (v1.6.0 — the user: "PCAN will not retransmit until you disconnect and reconnect"): `_ride_out` retries the *same* frame (built once, so neither a patched counter nor the TX tap double-counts it) after `_RECOVER_DELAYS` (0.2 → 3 s), calling `set_recover`'s `BusManager.recover` first — the adapter's own reset (PCAN `CAN_Reset`), every `_REOPEN_EVERY`-th try a close-and-reopen with the same settings, never for a bus the person disconnected — and when the frame goes out carries on from the next one on a fresh clock; the outage is `health.recoveries`/`outage_s` and added to the paused time, never to drift. Only Stop ends the wait. PCAN is also opened with `auto_reset=True` (`PCAN_BUSOFF_AUTORESET`), and `CANInterface.health()` (`hal.pcan_state`) reports the controller's error state — error-warning / error-passive is the adapter's blinking red LED while frames still go out — to the bus chip via `/ws/live` `bus_health`. **`health.keeping_up`** goes false once the timeline falls `_BEHIND_S` behind the wall clock — one thread plus one adapter tops out around 30 k frames/s, so a large speed multiplier can demand more than the machine delivers (measured: 20× on the Windsor drive wants 37 k fps, gets 29 k). The UI says so outright, because a silently smeared "real-time" replay makes the *device under test* look at fault. Repeat is `passes`: `1` once, `n` a count, `0` endless (`loop=True` is the legacy spelling). Endpoints: `/api/replay/{load,select,play,pause,resume,stop,step,speed,status}` — `load` takes `{path, network}` and returns per-network meta + **`warnings`** (discarded networks, bitrate mismatch vs the connected bus, >70 % load, skipped tool-TX), `select` re-targets network/ID-filter without re-parsing. `/api/logs` walks sub-folders (`_LOG_SCAN_DEPTH`) because real captures arrive as a folder per session, not loose files.
- `reverse.py` — pure-stdlib (`math` only) log analysis. Bit indices are **sequential MSB-first** (bit 0 = byte0/bit7); `dbc_builder.re_candidate_to_signal` converts that to cantools' big-endian start bit.
- `dbc_builder.py` — `DbcModel` keeps plain JSON-able dicts as the source of truth (the UI reads/writes them); cantools is only touched at export/import. **cantools 41.x uses a `conversion` object, not `scale`/`offset` kwargs** — see `_to_cantools_db`. `re_candidate_to_signal` converts a sequential-MSB-first bit index to a cantools big-endian start bit (reused by `convert.py`).
- `framedecode.py` — decode raw hex frames against a cantools DB into the BusMaster-style view: data bytes, per-signal raw/physical/unit/choice/OOR, and the `(byte,bit)` grid cells. `signal_cells`/`signal_msb_lsb` derive cells via the cantools packer (encode all-ones / a single bit) so Intel & Motorola both work without hand-rolled math. `_fmt_physical` does scale-aware decimals. **A payload shorter than the DLC pads on the *right*** (`_normalize`, and the same rule in `jsondecode.decode_frame`) — CAN payload bytes are positional, so byte 0 must stay byte 0; the earlier left-pad ("restore dropped leading zeros") silently shifted real short-DLC frames (MG Commute `0x120` is DLC 5: its odometer decoded 0.00 instead of the dash-confirmed 3066.53 km). Backs the Frame Decoder (`/api/decode/dbc-import`, `/api/decode/frames`). The Frame Decoder UI (`web/app.js`) has two modes: **Single** (one payload → byte view + signal table + Vector-style bit grid) and **Trace** (paste many payloads of one ID → change-highlighted matrix + const/varies summary + collapse-duplicates + CSV export); `/api/decode/frames` already takes a list of frames, so Trace decodes the whole sequence in one call with no backend change.
- `jsondecode.py` — self-contained decoder for the cloud **Signature JSON** (no cantools; the format carries no enums/min-max/units). Convention **validated against the Ziptron DBC** (see `docs/JSON_SIGNATURE_DECODE.md`): CAN-ID keys are **decimal in some exports, hex in others** — `detect_id_base` decides **per file** (a `0x` prefix, a hex letter, or zero-padding anywhere ⇒ the whole file is hex; else decimal), because `"120"` alone is ambiguous; `parse_frame_id`/`message_name`/`signal_list` are shared with `convert.json_to_model` so both readers agree. For **big-endian** (`reverse 0`) `startingBit` is **MSB-first sequential** (bit 0 = byte0 MSB) read MSB-first — equals the DBC Motorola layout, cantools start `= (start//8)*8 + (7 - start%8)`; for **little-endian** (`reverse 1`) it's LSB-first sequential; `signed`=two's complement. Ground truth: Ziptron 0x244 frame `5251 0047 C000 BA56` → `DTeInfo=287`, `HVBattSoCPercen=93`. Output dict shape **matches `framedecode`** so the Frame Decoder UI renders identically for DBC or JSON. `/api/decode/json-import`.
- `canplus.py` — importer for **CanPlus / telematics "vehicle library" configs** (`*.Config.XML`, root `<CanData>`). Decodes the 22-byte `<VarDesc>` records (verified: `b2-3`=VarID, `b8-9`=mult, `b10-11`=div, `b12-13`=offset, `b17-19`=source-frame signature) → canonical model grouped by frame-cluster. CAN id + bit layout are encrypted in the file, so only the two **field-validated** signals (Odometer `0x540`, Range/DTE `0x2A2`) get real layout; the rest are non-overlapping **placeholders** flagged in each signal's comment. Self-registers as a 4th Converter source format (`detect_format` matches `<CanData`); import-only (no serializer). See `docs/CANPLUS_CONFIG_DECODE.md`.
- `convert.py` — the model carries an **`id_base`** so JSON keys are written in the base the data came from: DBC ⇒ **16** (`"00000120"` — a DBC stores `BO_ 288` but the bus reads `0x120`, and cloud keys are hex), JSON ⇒ the detected base, CSV ⇒ **unset/decimal** (it has both id columns, so it cannot claim one; claiming hex would flip a decimal JSON on a CSV round trip). A **DBC hop cannot preserve the base or `evData`** — both are reported. DBC-sourced signals get **`ev_data: 1`** (a DBC has no such field and these are EV packs; it used to emit 0 for every signal), and **duplicate signal names are qualified by their message name**, not their CAN ID (`PackVoltage_HvPower`, not `PackVoltage_287`) because JSON consumers key on `fieldName` while a DBC scopes names per message — the message name says *why* two signals differ, and a DBC already guarantees names are unique within a message so it always disambiguates. `_qualifiers` strips a leading bus tag (`HSC_HvPower` → `HvPower`) detected as *few distinct first segments over many messages* (not "all share one prefix" — this DBC is 54 × `HSC_` + 1 × `MSC_Hvac`), keeps the strip **only if the shortened names stay unique**, and falls back to the hex id when a message has no real name (a JSON source auto-names them `MSG_<id>`). Renaming fires on duplicates *in the model being serialised*, so exporting a subset only renames what collides in that file. **DBC ⇄ JSON ⇄ CSV** converter over one canonical model (DbcModel-shaped dicts). `parse(text)`/`serialize(model,fmt)` + one-shot `convert()`; `detect_format` auto-detects source. Canonical `start_bit` is the JSON convention (MSB-first-seq for BE, LSB-seq for LE); JSON & CSV use it directly, and the **DBC** boundary converts via the self-inverse `(x//8)*8 + (7 - x%8)` for big-endian — exact both ways (no sub-byte ambiguity). CSV carries both `CAN ID (HEX)` & `CAN ID (Dec)`, `Motorola`/`Intel`, value tables. Endpoints `/api/convert` (one-shot) + `/api/convert/{parse,export}` (the upload→edit/select→download workbench).
- `signals.py` — `SignalViewer.consume` is the tap: decodes each frame against a loaded DBC into bounded per-signal `(t, value)` ring buffers. Non-numeric (choice) signals are skipped, not raised. `decode_frames_offline` is the log-playback counterpart (read-only w.r.t. the live buffers). `info()` also returns each signal's `minimum`/`maximum`/`length`/`is_signed` — the Signal Viewer's summary panel flags decoded values that fall outside the DBC's own declared range, the fastest tell for a wrong scale/length/signedness.
- **Signal Viewer front end (`web/app.js`)** — two views over one dataset, toggled Table/Chart with **Table as the default**. Both read the same decoded series, so the table needs no backend. Key invariants: rows are built **lazily for the visible window only** (`sigBuildRows` walks a forward cursor per column into the already-sorted series — never materialise a matrix); a value is **stale/grey when older than ~3× *that signal's own* median period** (`sigBuildMeta`), *not* when a grid row carries no fresh frame — the naive rule makes a healthy 100 ms signal strobe grey on a 10 ms grid; one **zoom** drives both the chart window and the table row interval so "time resolution" means one thing. Chart mode centres the playhead (log) / trails it (live). Export: CSV is client-side, `.xlsx` goes through `/api/signals/export-xlsx` because only Excel can carry the held/changed cell colouring. **Nav readiness (`VIEW_READY` + `applyAvailability()` in `web/app.js`)** — the sidebar states what each tab needs, so a tab that shows nothing never reads as broken. Three kinds, and **a view absent from the table is a promise that it works as-is**: `bus` dims the item and shows a "Bus" pill *only while disconnected* (still clickable — a disabled nav item hides what the tool can do; an in-view `.view-gate` repeats the reason), `input` keeps full brightness with a standing "Log"/"DBC"/"File" pill (built, works offline, needs a file), `soon` **is left out of the rail altogether** (since 2026-11-24, at the user's request: a greyed "Soon" row still read as clutter) and `openView()` refuses it (an empty reachable panel is what looks like a bug). There is **no legend**: each pill explains itself in a hold-tip (`PILL_TIPS`, or the entry's own `why`), and `tests/test_ui.py` checks every `VIEW_READY` entry has one. A held-back view can still be switched on per browser in **Settings → Views** — it then shows with a "Preview" pill. **`soon` means "not available to the user", not "not written"** — as of 2026-08-04 `re`, `autore`, `dbc` and `decoder` are tagged `soon` *by product decision* while remaining fully implemented and covered by tests; each line records the `kind` to restore when it ships (`replay` was tagged and then resumed back to `bus`). Only `oem` needs neither a bus nor a file. Two invariants when editing the table: the startup view (`dashboard`) must never be `soon`, and neither may any `goView()` target (`framedec`, `convert`) — both would silently dead-end.
- `dashboard.py` — `Dashboard.consume` is a tap that decodes *standardised* parameters (no DBC): `OBD_PIDS` (Mode-01 PID responses) and `J1939_PGNS` (SPN tables, little-endian, with 0xFF.. = not-available). Keeps only the latest value per parameter, grouped by standard; entries older than 3 s are flagged `stale`. Extend by adding table rows — consume/snapshot need no changes. The simulator (`sim._emit_standard`) emits matching OBD-II + J1939 demo frames so the Dashboard populates on the virtual bus.
- `dtc.py` — `DtcMonitor.consume` is a tap decoding trouble codes: OBD-II Mode 03/07/0A (`0x43/0x47/0x4A`, 2-byte → `P/C/B/U`), UDS `0x59` ReadDTCInformation (3-byte DTC + status byte → flag names; records start *after* SID+subfunc+availability-mask), and J1939 DM1/DM2 (`PGN 0xFECA/0xFECB`, 4-byte → SPN/FMI/OC). Dedupes by code with an occurrence (`seen`) counter; >5 s old = `stale`. OBD/UDS need a request, so `/api/dtc/scan` transmits Mode 03/07 + a J1939 DM1 request; J1939 DM1 is broadcast so it appears passively. `/api/dtc/clear` clears only the local list; `/api/dtc/clear-ecu` sends OBD Mode 04 (a real vehicle write — UI confirms first). Demo frames come from `sim._emit_standard`.
- `protocol.py` — stateful `ProtocolDecoder` with ISO-TP reassembly (First/Consecutive frames buffered per ID). 29-bit IDs are decoded as J1939; OBD falls through to UDS when the mode isn't a known OBD mode (handles a `0x7F` NRC on a `0x7E8` ID).
- `bus_manager.py` — **one** `BusManager` instance (held by `server.py`) is the whole app's mutable bus state: current `iface`, its `CanLogger`, the optional `sim` feeder, plus a persistent **tap registry** re-applied to each new logger on connect (so taps survive reconnects) and a `send` passthrough.
- `server.py` — instantiates one of every subsystem, registers `viewer.consume` + `_proto_tap` as bus taps once at import, and exposes the REST control plane + `/ws/live` (pushes `logger.snapshot()` **and** `replayer.status()` at ~5 Hz). Static mount of `web/` is registered **last** so `/api` and `/ws` win.

### Recording vs. live capture

The logger always captures into in-memory stats once connected. **Recording** is separate: `start_recording(fmt, path)` opens a `python-can` writer (`ASCWriter`/`BLFWriter`/`CSVWriter` per the `_WRITERS` map) and streams frames straight to disk under `data/logs/`, so arbitrarily long logs never accumulate in memory. The active writer is fed inside the same locked `_ingest` path.

### Gotchas

- **Two label-layout-style twins don't exist here, but a similar coupling does:** when you change the `snapshot()` shape in `logger.py`, update `web/app.js` `render()` which reads those exact keys.
- **WebSocket pushes aggregates, not per-frame events** — at 290+ fps, per-frame WS would flood the UI. Keep new live data in the snapshot, not in new high-rate socket messages.
- **Threading:** all of `CanLogger`'s mutable state is guarded by `self._lock`; any new read/write of stats must take it. The recv thread is a daemon and joined with a timeout on stop.
- **All seven modules are implemented.** The capture→analyze→transmit loop is closed: Logger records → RE finds candidate signals → DBC Builder emits a `.dbc` → Signal Viewer decodes the live bus → Replay/Scheduler transmit. New work extends this; the per-PID/PGN tables in `protocol.py` and the candidate-signal heuristics in `reverse.py` are the most likely places to deepen.
- **`can.LogReader` cannot read a Vehicle Spy CSV.** It dispatches on *extension*, so a neoVI export hits its own `timestamp,arbitration_id,…` dialect and fails. Anything that opens a log must go through `logstore.load()` (TX) or `reverse.load_log_frames()` (RE), both of which sniff the banner first. This is why TX replay couldn't load a single MG Commute file before TX-1.
- **A `.trc` timestamp is not what `can.LogReader` says it is.** PCAN-View's `O` column is the driver's hardware timer (it keeps running across trace start/stop, so a file recorded ten minutes in opens at `O = 600000`), and `$STARTTIME` is *local* time there but *UTC* in a `can.TRCWriter` file. `can.LogReader` adds the raw offset to a UTC-read start time, so it is wrong by the timezone **plus** the offset — measured at +5:30 +131.4 s on a real capture. Deltas are unaffected, which is why single-file replay looked fine and the bug hid: it only surfaces where files are *compared*, i.e. `gap_before_ms="auto"`, where it made 10 of the Dzire session's 13 consecutive pairs look like they overlapped. Anything reading a `.trc` for cross-file work must go through `logstore.load()`; `reverse.load_log_frames()` still uses `can.LogReader` and is fine only because RE is single-file and relative.
- **A bitrate without its provenance is a lie waiting to happen.** `.trc` records none at any version, so `pcantrc` assumes 500 kbit/s — which then feeds the bus-load figure *and* the "reconnect, wrong bitrate" warning. Both would be stating the log's word for something the log never said, so `baud_source` (`log`/`declared`/`assumed`/`none`) travels with the number to `_replay_warnings`, and the wording differs per source. Never add a consumer of `meta["baud"]` that ignores `meta["baud_source"]`.
- **One log file ≠ one bus.** Vehicle Spy interleaves every network it was wired to. Transmitting a whole file onto one channel merges traffic that never coexisted (and can collide IDs), so TX always selects a single network. Multi-channel simultaneous TX needs `BusManager` to hold more than one `iface` — it currently holds exactly one.
- **Path arg gotcha:** REST endpoints that take a log/DBC `path` receive it as JSON — Windows backslash paths are invalid JSON escapes. The UI uploads files (multipart → `data/uploads/`) and passes the returned server path, so this only bites hand-rolled `curl` tests; use forward slashes there.
- **The UI is plain JS, polled per-view.** `web/app.js` switches a single `pollTimer` on nav change (signals/scheduler/decoder poll their REST endpoints; logger + replay ride the WebSocket). Strip charts are hand-drawn on `<canvas>` — no chart library.
